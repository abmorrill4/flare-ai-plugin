# docstyle: Google style + company style, applied the same way everywhere

The style guide is one Flare project (`styleguide/`) with two folders: **Google** (the Google developer documentation
style guide, compiled into rules) and **Company** (the team's rules, which win on any conflict). The open docs
project adds its own layer (variables, glossary) on top. The same engine drives the FlareAI plugin in Flare and this
MCP server (`tools/FlareAI.Mcp`). Never invent a rule that is in neither layer. When unsure, call `style_lookup` and
cite the rule id.

## Tools (docstyle MCP server)
- `lint(texts, headings)`: one string per text run (no markup); `headings` = indices of runs that are headings.
  Returns exact spans, the rule, its id and layer (`google`, `company`, `project`), a guide link, and an exact
  `replacement` when the fix is mechanical (`null` when it needs judgment).
- `style_lookup(query)`: matching rules from every layer (with `applies` content tags and `products`); `""` returns
  the full layered guide.
- `glossary_lookup(term)`: canonical spelling, abbreviation, first-use note (`""` lists every entry).
- `validate_guide(project)` / `guide_examples(project)`: test the guide itself.
- `mine_style(project)`: proposed rules from a Flare project's own content, minus what the guide already enforces.

`FlareAI.Mcp.exe --llm-export OUTPUT_DIR [--url BASE]` turns built Flare HTML into Markdown per topic +
`llms.txt` / `llms-full.txt`.

Pass `project` (any path inside a MadCap Flare project) to add that project's layer.

If the server is not connected (build it: `dotnet build tools/FlareAI.Mcp`), say so and fall back to the `.htm`
topics in `styleguide/Content/Resources/StyleGuide/`.

## Review workflow (check style)
1. Split the content into text runs (text between tags). Never lint or quote across markup.
2. Call `lint`. These findings are authoritative and come first; don't restate them in your own words.
3. Do one judgment pass for what a linter cannot catch, using the rules that apply to the content (a rule's
   `applies` tags say which content it's for: Steps, Code, UI…). Report a problem only if a careful editor would
   change it before publishing; at most two per paragraph.
4. Report every finding as: **excerpt** (verbatim, shortest unique span inside one run) → **replacement**
   (exact text, or "needs rewrite") — *why* (≤ 15 words, cite the rule id).

## Edit workflow (rewrite)
- Fix every lint finding plus clear style breaks; leave compliant sentences word-for-word. Never add facts the text
  doesn't have.
- Re-run `lint` on your result and fix what is left before returning it.

## Flare / XHTML constraints (non-negotiable)
- Preserve every `MadCap:` element and attribute exactly (variables, xrefs, snippets, conditions, drop-downs).
  Never add one. Keep `href`, `src`, `id`, `name`, `MadCap:conditions` unchanged.
- Don't quote or edit text inside snippets, variables, index keywords, or code (`code`, `pre`, `kbd`).
- Output well-formed XHTML; keep the block structure unless asked to restructure.

## Changing the rules
- Edit `Company/` topics only; `Google/` is generated by `tools/FlareAI.GuideCompiler`.
- Bullets are prose rules (nested `Bad:`/`Good:` make them testable); Avoid/Use (or Pattern/Use) tables become lint
  rules; a Rule/Setting/Reason table turns a rule off or changes its level by id (`google:numbers/3`).
- Content condition tags scope a rule to sections with that content; Product tags limit it to products listed in the
  guide's Product tag set.
- After changes: `validate_guide` and `dotnet test`.
