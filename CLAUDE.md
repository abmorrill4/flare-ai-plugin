# CLAUDE.md — working notes for coding sessions in this repo

## What this is
A MadCap Flare Desktop plugin (`src/FlareAI.Flare`, net40) over a Flare-agnostic core
(`src/FlareAI.Core`, net40). Plan and architecture: `PLAN.md`. Flare API facts we rely on:
`docs/flare-api-notes.md`. Real API surface from the installed DLL: `docs/api-dump.txt`
(generated by `scripts/dump-api.ps1` — regenerate after a Flare upgrade).

## Hard constraints
- `FlareAI.Core` targets **net40**; `FlareAI.Flare` targets **net48** because Flare 22's
  `B3.PluginAPIKit.dll` is built for .NET 4.8 (the docs' "4.0" is outdated). Keep old-runtime idioms anyway: No `async`/`await`,
  no `HttpClient`, no `ValueTuple`, no `System.Text.Json`. Use `HttpWebRequest`, Newtonsoft.Json,
  `BackgroundWorker`/`ThreadPool`.
- `FlareAI.Core` must never reference `B3.PluginAPIKit` or WPF/WinForms. Keep it testable on any OS.
- Every DOM write is a tracked change in one undo step, through `IDocumentAdapter` only:
  `ReplaceBlocks(...)` for validated block rewrites, `Edit(op, () => ReplaceSpan(...))` for word-level fixes.
  Never call `ReplaceDocumentNode` with an unvalidated fragment. Read the "Verified write behavior" section
  of `docs/flare-api-notes.md` before touching `FlareDocumentAdapter` — most obvious approaches fail in Flare 22.
- Style rules live only in the style guide project (`styleguide/Content/Resources/StyleGuide/Google` and `/Company`,
  a team's configured guide project, or a docs project's variables/glossary/StyleGuide). Don't hard-code style rules
  in prompts or C#. `Google/` is generated by `tools/FlareAI.GuideCompiler` from `tools/google-style/source`: never
  hand-edit it; change Google rules from `Company/` (Rule/Setting table) instead.
- Everything ships inside the plugin folder: no Python, uv or Vale at runtime. `StyleEngine` (Core) is the guide,
  linter, validator and miner; `tools/FlareAI.Mcp` exposes the same engine over MCP.
- Never log or print the API key. Settings use DPAPI; dev fallback is the `ANTHROPIC_API_KEY`
  env var, loaded from the git-ignored `.env` at the repo root by `scripts\Load-DotEnv.ps1`.

## Commands
```powershell
powershell.exe -File .\scripts\bootstrap.ps1   # first run; needs Windows PowerShell 5.1 (ReflectionOnly API)
dotnet build FlareAI.sln -c Debug
dotnet test
.\scripts\install-plugin.ps1   # admin
.\scripts\run-flare.ps1        # Flare + injected key
.\scripts\smoke-api.ps1        # verify key/model from this machine
.\tools\FlareAI.Bench\bin\Debug\net48\FlareAI.Bench.exe --no-ai   # lint the 250-topic corpus against ground truth
uv run --script tools\google-style\snapshot.py                      # refresh the Google guide snapshot (maintainers)
.\tools\FlareAI.GuideCompiler\bin\Debug\net48\FlareAI.GuideCompiler.exe   # recompile changed Google pages (~$, Opus)
```

## When the build fails against the real DLL
The Flare docs are thin; `docs/api-dump.txt` is authoritative. Typical fixes: namespace of
`RibbonControlData`/`ButtonCommand`, the `ICommand` type the ribbon expects, `AddRibbonButton`
return type. Fix in `src/FlareAI.Flare/Plugin.cs` only; do not leak Flare types into Core.

## Style
C# 7.3 features are fine (the compiler is modern; the runtime target is old). Prefer small
classes, explicit names, XML doc comments on public Core types.
