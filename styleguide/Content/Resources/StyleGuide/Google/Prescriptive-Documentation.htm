Prescriptive documentation

Write prescriptive documentation

  • Recommend a way to achieve tasks and tell the reader what to do instead of giving them a list of options to choose from; when a task involves multiple approaches or products, recommend a path.
  • State a clear, specific purpose for the document, and write headings and content with that purpose in mind.
  • Make example scenarios and procedures reflect the use cases that are most likely relevant to the readers.
  • Provide sample commands and arguments that accomplish the task for the most common use case.

Word choice for recommendations and requirements

  • To indicate required or optional user actions or the outcomes of a process, select an appropriate auxiliary verb such as must, can, or might, and generally avoid the word should.
    • Bad: The Classroom Share Button should conform to our min-max size guidelines and related color and button templates.
    • Good: Ensure that the Classroom Share Button conforms to our min-max size guidelines and related color/button templates.
  • Determine whether an action is required versus optional, an outcome is expected versus possible, or a state is actual versus recommended.
  • If an action is required, use must, or rephrase the sentence so that it's a clear imperative instruction such as "Do the following before you continue."
    • Bad: Whether it's a brand new project or an existing one, here's what you should do.
    • Good: Whether it's a brand new project or an existing one, perform the following steps.
  • If an action is recommended, use "We recommend" or "Google recommends"; use should only if the recommended action is generally recognized, such as "You should use a strong password."
  • If an action is optional, use can, as in "You can also use approach B to solve the same problem."
    • Good: You can also use approach B to solve the same problem.
  • If an outcome is expected, describe the outcome in terms of what is expected, as in "The process returns 10 items."
    • Good: The process returns 10 items.
  • If an outcome is possible, use might or can, as in "The process can take about 30 minutes."
    • Good: The process can take about 30 minutes.
  • When you describe the state of something, such as the value of a variable, avoid writing "The value should be true"; instead clarify whether you mean "You must set the value to true," "The server sets the value to true," or "If the value is false, follow these steps to change it to true."
    • Bad: The column of the data table that the filter should operate on.
    • Good: The column of the data table that the filter operates on.
