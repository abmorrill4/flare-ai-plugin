Tables

List or table?

  • When each item is a single unit, such as a programming language name or a step to follow, use a numbered list, lettered list, or bulleted list.
  • When each item is a pair of pieces of related data, such as term/definition pairs, use a description list (or, in some contexts, a table).
  • When each item is three or more pieces of related data, such as parameters with a name, a data type, and a description, use a table.

Places not to use tables

  • Don't use tables to lay out a page; use your site's standard CSS instead.
  • If you have only one row of material, usually don't use a table, except in some contexts such as consistency of layout in reference documentation.
  • If you have only one column in your table, turn the table into a list.
  • Don't use tables to lay out code snippets.
  • Don't use tables to lay out long one-dimensional lists in multiple columns; use tables only to present two-dimensional data that semantically makes sense to display in rows and columns.
  • Avoid tables in the middle of a numbered procedure.

Multi-paragraph table cells

  • To create multiple paragraphs in a table cell, use the p element rather than the br element.

Introductory sentences for tables

  • Introduce tables with a complete sentence that describes the purpose of the table.
    • Good: Change the environment variables to values for your deployment, as listed in the following table:
  • End the introductory sentence with a colon if it immediately precedes the table, and usually with a period if there's more material (such as a note paragraph) between the introduction and the table.

Table placement

  • When introducing a table, try to refer to the table's position, using a phrase like the following table or the preceding table.
  • Don't put a table in the middle of a sentence.
  • Avoid using footnotes in tables when possible.
  • If your table refers to footnotes, place them immediately following the table.

Table captions

  • Place the table adjacent to the text that refers to it.
  • If your document contains more than one table in fairly close proximity to each other, include a caption for each one, using a caption element as the first child of the table element.
    • Good: <table> <caption><b>Table 1.</b> Prehistoric birds</caption> ... </table>
  • Start the caption with a number, in the form "<b>Table NUMBER.</b> DESCRIPTION", and use sentence case for the caption.
    • Good: <table> <caption><b>Table 1.</b> Prehistoric birds</caption> ... </table>
  • When referring to a captioned table from text, refer to it by its number—for example, as shown in table 2.
    • Good: ... as shown in table 2.

Table formatting

  • Don't add styling to the table element.
  • Don't apply a visual style such as a different font, font color, or background color to convey a header row or column by itself; use the th element to semantically mark up headers in tables.
  • Sort rows in a logical order, or alphabetically if there is no logical order.
  • If the table is long or complicated—for example, with multiple header rows or columns—consider splitting it into multiple tables.
  • Don't present new information in tables through images or symbols alone; always provide a descriptive alt attribute for the image or symbol.

Table column heads

  • Use sentence case for table column heads.
  • Write concise table column headings.
  • Use table headings for the first column and the first row only.
  • Include the scope attribute on table headings as appropriate for accessibility.
PatternUseSeverityWhyExample
(?:\.|:|…)\s*</th>warning<th>Description:</th>

Responsive tables

  • Where possible, use table CSS that adapts to different viewport sizes.

Link to tables

  • Where possible, avoid linking to tables; instead, refer to them by table number.
