Example domains and names

  • Don't use real domain names, email addresses, or people's names in your examples.
  • Don't reveal personally identifiable information (PII), such as domain names, email addresses, phone numbers, people's names, project names, or credit card numbers; provide imaginary (fictitious) examples or use placeholders, like USER_ID or EMAIL_ADDRESS.

Example domain names

  • When you need a generic domain name in an example, use example.com, example.org, or example.net, or one of the domains Google owns for documentation: altostrat.com, examplepetstore.com, example-pet-store.com, myownpersonaldomain.com, my-own-personal-domain.com, or cymbalgroup.com.
  • If you need an example domain name for an internationalized domain name, use one of the IDN Test TLDs and copy from the "URL of the test site" column.
    • Good: Hostnames that include non-ASCII characters are encoded using Punycode. For example, http://مثال.إختبار is encoded as xn--kgbechtv.

Example email addresses

  • If you need a generic email address, use one of the listed example domain names and one of the listed example person names—for example, dana@example.com; generic addresses like support@example.net are OK.
    • Good: dana@example.com
  • Don't use person names, product names, or made-up names in email addresses.

Example person names

  • When you need to include example given names, draw from the following list: Alex, Amal, Ariel, Bola, Charlie, Cruz, Dana, Dani, Hao, Ira, Izumi, Jie, Kai, Kalani, Kim, Kiran, Lee, Lucian, Luka, Mahan, Noam, Nur, Quinn, Raha, Rosario, Sasha, Tal, Taylor, Tristan, Yuri.

Example person surnames

  • When you need to include example surnames, use an initial after the given first name—for example, Quinn N. or Dana A.
    • Good: Quinn N.

Further notes about example people

  • Strive to include a variety of people in your examples, so that real readers with different jobs, cultural contexts, and backgrounds feel respected, valued, and welcomed.
  • Use the gender-neutral singular pronouns they, their, and theirs whenever possible, and avoid specifying gender unless it is integral to the information you are communicating.
  • Avoid examples that depend on a gender binary.
  • If an example requires specifying gender, check that the names you have chosen do not carry a conflicting gender connotation in a given language or culture.
  • Be mindful of assumptions and stereotypes that hypothetical examples might reinforce, such as job roles and levels (like executive) disproportionately assigned gendered personas, or job roles (like developer or engineer) disproportionately assigned particular ethnic personas.
  • Don't use the Alice and Bob characters unless you're writing documentation that refers to a technical specification that uses those characters.
  • If you use the Alice and Bob characters in a document, use only names from that cast of characters.

Example company names

  • When you need a company name in an example, use Example Organization; to differentiate between two fictional companies, add a description, such as Enterprise Example Organization and Startup Example Organization.

Example IP addresses

  • When you need an IPv4 address in an example, such as in a log, use one of the RFC 5737 addresses reserved for documentation: 192.0.2.0 through 192.0.2.255, 198.51.100.0 through 198.51.100.255, or 203.0.113.0 through 203.0.113.255.
  • For IPv4 address ranges, use 192.0.2.0/24, 198.51.100.0/24, or 203.0.113.0/24.
  • When you need an IPv6 address, use values from the RFC 3849 range, such as 2001:db8::, 2001:db8:ffff:ffff:ffff:ffff:ffff:ffff, or 2001:db8:1:1:1:1:1:1.
  • For IPv6 address ranges, use 2001:db8::/32.

Example street addresses

  • Avoid using real street addresses in examples; instead, use one of these fictional addresses: 1800 Amphibious Blvd. Mountain View, CA 94045; Avenida da Pastelaria, 1903 Lisbon, 1229-076; or 8 Rue du Nom Fictif 341 Paris.

Example project names

  • When you need an example project name, create a name that's meaningful or descriptive and applicable to the reader's environment.
  • Don't use unclear components like foo, bar, and baz in names.
  • When necessary, use an appended numbering scheme for project names, for example, production-1, production-2.
    • Good: staging, frontend-development, backend-development, production-1, production-2
