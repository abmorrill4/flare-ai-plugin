Use clear, concise, and unambiguous language

  • Consider global audiences and translation and write in a way that's clear, concise, and unambiguous.

Use simpler words and shorter sentences

  • Use a simple word: don't use commence when you mean start or begin, consequently when you mean so, or utilize or leverage when you mean use.
  • Use a single word when it conveys the same idea as a phrase; for example, don't use a number of when you can use some or many.
  • Write shorter sentences.

Avoid phrasal verbs

  • Avoid phrasal verbs when possible; try to substitute a simpler verb first (exceptions include set up, log in, and sign in).
    • Bad: This document makes use of the following terms:
    • Good: This document uses the following terms:

Use modifiers appropriately

  • Don't use too many modifiers; in particular, don't use more than two nouns as modifiers of another noun.
    • Bad: A hybrid cloud-native DevSecOps pipeline
    • Good: A cloud-native DevSecOps pipeline in a hybrid environment
  • Don't misplace modifiers; place a word like only immediately before the word or phrase that it relates to, and rephrase if the meaning is still ambiguous.
    • Bad: Only request one token.
    • Good: Request only one token.
  • Describe technical details in precise, technical terms, and avoid subjective modifiers such as simply, properly, or carefully.

Use active voice and present tense

  • Use present tense.
  • Avoid complex or uncommon verb forms.
  • Use active voice, where the subject of the sentence is the person or thing performing the action.
  • Avoid participles and gerunds (verbing) when possible; consider replacing using with by using, that use, or you use as appropriate.
    • Bad: Configuring the VPC firewall rules is required before deploying the VM instance.
    • Good: You must configure the VPC firewall rules before you deploy the VM instance.

Use words in their primary sense

  • Don't use the same word to mean different things; in particular, avoid using the same word as both a noun and a verb in close proximity.
  • Avoid directional language (for example, above or below) in procedural documentation.

Use helper words and optional words

  • Use qualifying nouns for technical keywords; for example, call a file the example.yaml file and not example.yaml by itself.
  • Repeat a word if the redundancy improves comprehension.
    • Bad: If the VM has started and you're able to connect...
    • Good: If the VM has started and if you're able to connect...
  • Use helper words such as then, that, and of to avoid ambiguity.
    • Bad: If the attribute key is not found, the default value is returned.
    • Good: If the attribute key is not found, then the default value is returned.
  • Don't omit relative pronouns; use relative pronouns such as that and which.
    • Bad: You can programmatically update the rules you previously defined.
    • Good: You can programmatically update the rules that you previously defined.

Clarify abbreviations and pronouns

  • Define abbreviations: spell things out whenever possible, at least the first time that you use a given term.
  • Clarify antecedents: if a pronoun is ambiguous, then replace it with the appropriate noun.
    • Bad: If you use the term green beer in an ad, then make sure that it's targeted.
    • Good: If you use the term green beer in an ad, then make sure that the ad is targeted.

Use apostrophes appropriately

  • Don't form a plural with 's.
  • Don't use the plural or possessive form with trademarks of company, product, and feature names.
  • Don't use uncommon contractions.

Address users and their needs directly

  • Address the user and their needs directly and avoid providing unnecessary information.
  • Address the reader directly: use you instead of the user or they, unless you're referring to someone who uses the software that the reader is developing.
  • Provide context; don't assume that the reader already knows what you're talking about.
  • Avoid negative constructions when possible; consider whether it's necessary to tell the reader what they can't do instead of what they can.

Be consistent

  • Use standard sentence structures, consistent terminology, and appropriate punctuation to avoid creating barriers to understanding, ambiguity, and mistranslations.

Use consistent terminology

  • If you use a particular term for a concept in one place, then use that exact same term elsewhere, including the same capitalization.

Use standard sentence structures and formatting

  • Use standardized phrases for frequently used sentences, introductory phrases, and other common tasks, such as introducing links, output, and code samples.
  • Use standard English word order: subject + verb + object.
  • Try to keep the main subject and verb as close to the beginning of the sentence as possible.
  • Use the conditional clause first: mention the circumstance before you provide the instruction.
  • Make list items parallel in structure.
  • Be consistent in the capitalization and punctuation of list items.

Use consistent text formatting

  • Use consistent typographic formats: use bold and italics consistently, and don't switch from using italics for emphasis to underlining.
  • Use consistent capitalization.

Be inclusive

  • You're not writing for your culture; write with inclusivity in mind.
  • Write dates and times in unambiguous and clear ways.
  • Don't be too culturally specific; don't refer to specific holidays, cultural practices, or sports unless you're certain they're known worldwide.
  • If you need to use people's names (for example, as email addresses), use a diverse set of names.
  • Avoid colloquialisms, idioms, or slang.
  • Avoid humor.
  • Avoid geographically specific references, like the seasons.

Consider accessibility for images

  • Use screenshots and text in figures sparingly.
  • Convey any new information through text, not by introducing it in a figure or image.
