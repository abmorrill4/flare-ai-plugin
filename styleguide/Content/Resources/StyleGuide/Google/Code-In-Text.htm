Code in text

  • In ordinary text sentences, use code font to mark up most things that have anything to do with code.
  • To mark text as code font in HTML, use the code element.

Some specific items to put in code font

  • Put attribute names and values in code font.
    • Good: You can create a VM instance using the e2-highcpu-16 machine type in the us-central1-a region.
  • Put class names in code font.
    • Good: The SnapshotDiskOperator class includes the generate_snapshot_name method.
  • Put command output in code font.
    • Good: The output is similar to the following: Found sysprep-specialize-script-ps1 in metadata. ... Finished running specialize scripts.
  • Put command-line utility names, such as gcloud, gsutil, kubectl, and bq, in code font.
    • Good: You can use the kubectl tool to define a network policy.
  • Put data types in code font.
    • Good: Nested data is represented as a STRUCT type.
  • Put database elements, such as row and column names, in code font.
    • Good: The query extracts the month, julianday, and dayofweek values from the datetime and timestamp columns.
  • Put defined (constant) values for an element or attribute in code font.
    • Good: The constant city has the value "San Francisco".
  • Put DNS record types in code font.
    • Good: Create a DNS AAAA record in your public DNS zone that points to the IP address of the load balancer.
  • Put HTML and XML element names in code font.
    • Good: The script and df-messenger HTML elements should be in the body element of your page.
  • When you refer to an element name, don't put angle brackets (<>) around the element name.
    • Good: A C-CDA document contains a header and a body enclosed within a ClinicalDocument XML element.
  • Put enum (enumerator) names in code font.
    • Good: Generated from the protobuf enum BOOL = 1;.
  • Put environment variable names in code font.

  • Put folder and directory names in code font.

  • Put HTTP content-type values in code font.

    • Good: The HTTP 500 Internal Server Error status code indicates that the server encountered an unexpected condition that prevented it from fulfilling the request.

    • Good: The logID field includes the domain corpaudits.example.com.

  • Generally, don't put quotation marks around code unless the quotation marks are part of the code.

Items to put in ordinary (non-code) font

  • Put domain names, names of products, services, and organizations, and URLs that the reader follows in a browser in ordinary (non-code) font.
    • Good: The test environment is designed only for standard application offerings from example.com.
  • If you're referring to any of these items as computer input or output, or as a code entity like an attribute or value, then use code font.
  • It's usually best to format a URL as a link and use descriptive link text instead of exposing the URL itself.

Code in UI elements

  • If a UI element meets the requirements for code font, then use both code font and bold for that element.
    • Good: In the Network list, select my-net-2.

Items that are sometimes in code font

  • If you refer directly to a Boolean data type value (such as true or false, or 1 or 0), format the value as code; if you refer to the evaluation of a Boolean condition as true or false, use non-code font.
    • Good: If the update succeeds, returns true.
  • When a command-line utility name is spelled the same as its software project or product, use code font for the command and ordinary font for the name of the project or product.
    • Good: The options for the curl command are explained on the curl project website.
  • If you want the reader to use the email address as computer input or output, use code font.
    • Good: Enter the username, not the full email address. For example, enter alex, not alex@example.com.
  • If you want the reader to treat the email address as a way to contact someone or a reference to someone, use non-code font and hyperlink the email address.
    • Good: For help, contact support@example.com.

Method names

  • When you refer to a method name in text, omit the class name except where including it would prevent ambiguity.
    • Bad: To retrieve the zebra's metadata, call its animal.get method.
    • Good: To retrieve the zebra's metadata, call its get method.

HTTP status codes

  • To refer to a single HTTP status code, use the form "an HTTP 400 Bad Request status code" and put the number and the name in code font; if the HTTP is implicit from context, you can leave it out.
    • Good: an HTTP 400 Bad Request status code
  • Call an HTTP status code a status code instead of a response code or error code.
    • Good: an HTTP 400 Bad Request status code
  • To refer to a range of status codes, use Nxx (with a specific digit in place of N) to indicate anything in the N00-N99 range, and put the status code number in code font even if you're leaving out the code's name.
    • Good: an HTTP 2xx or 400 status code
  • If you specify an exact range of status codes, put the numbers in code font.
    • Good: an HTTP status code in the 200-299 range

Grammatical treatment of code elements

  • Don't use code elements such as keywords and filenames as if they were English verbs.
    • Bad: POST the data.
    • Good: To add the data, send a POST request.
  • Don't inflect the name of a code element, such as to make it plural or possessive; instead, include a noun after the name of the code element, and inflect that noun.
    • Bad: ADDRESS's value is defined in settings.h.
    • Good: The ADDRESS constant's value is defined in the settings.h file.

Linking API terms in Android

  • In code comments that you'll turn into generated reference documentation, link to the first instance of each element of Android APIs, such as classes, methods, constants, and XML attributes, using code font and regular HTML a elements.
  • For later uses of the same API element in the same section, use code font but do not link to the reference documentation.
  • Link AndroidManifest.xml elements and attributes to the API guide pages.
    • Good: <a href="/guide/topics/manifest/data-element.html">data</a>
  • Link the attribute for a particular widget or layout to its Javadoc in the widget or layout's API reference entry, using the page URL plus the fragment identifier #attr_android:ATTRIBUTE_NAME.
    • Good: <a href="/reference/android/widget/TextView.html#attr_android:inputType">inputType</a>
  • Very common classes such as Activity and Intent don't need to be linked every time.
  • If you use a term such as activity, service, fragment, view, loader, action bar, intent, content provider, broadcast receiver, or app widget as a concept rather than a class, don't put it in code font and don't capitalize it.
    • Good: The user interface for an activity is provided by a hierarchy of views—objects derived from the View class.
  • If you use one of these terms in the context of referring to an actual instance, use the formal class name and link to its reference page.
    • Good: The Activity class is an important part of an application's overall lifecycle...
  • To link to a class, use the class name as link text.
    • Good: <a href="/reference/android/widget/TextView">TextView</a>
  • To link to a method, use the method name as a fragment identifier.
    • Good: <a href="/reference/android/app/Activity.html#onCreate(android.os.Bundle)">onCreate(Bundle)</a>
  • If you're linking to a static method, also include the class name in the link text.
  • If you need to distinguish between overloaded versions of a particular method, consider showing the full signature.
    • Good: <a href="/reference/android/app/Activity.html#onCreate(android.os.Bundle)">onCreate(Bundle)</a>
