API reference code comments

Documentation basics

  • Provide a description for every class, interface, struct, and any other similar member of the API (such as union types in C++).
  • Provide a description for every constant, field, enum, and typedef.
  • Provide a description for every method, with a description for each parameter, the return value, and any exceptions thrown.
  • On each unique page (for a class, interface, etc.), include a code sample (~5-20 lines) at the top.
  • Put all API names, classes, methods, constants, and parameters in code font.
  • Link each API name, class, method, constant, and parameter to the corresponding reference page.
  • Put string literals in code font, and enclose them in double quotation marks.
    • Good: "wrap_content"
  • Make sure that the spelling of a class name in documentation matches the spelling in code, with capital letters and no spaces.
    • Good: ActionBar
  • Don't make class names plural; instead, add a plural noun.
    • Bad: Intents, Activities
    • Good: Intent objects, Activity instances
  • If a class has a name that's a common term, you can refer to it with the corresponding English word, in lowercase and not in code font.
    • Good: activities, action bar

Classes, interfaces, structs

  • In the first sentence of a class description, briefly state the intended purpose or function of the class or interface with information that can't be deduced from the class name and signature.
    • Good: A primary toolbar within the activity that may display the activity title, application-level navigation affordances, and other interactive items.
  • In additional class documentation, elaborate on how to use the API, including how to invoke or instantiate it, what some of the key features are, and any best practices or pitfalls.
  • Make the first sentence of each class description unique and descriptive, yet short.
  • Don't repeat the class name in the first sentence.
  • Don't say "this class will/does ..." in a class description.
  • Don't use a period before the actual end of the first sentence, because some document generators naively terminate the short description at the first period.

Members

  • Make descriptions for members (constants and fields) as brief as possible.
    • Good: Show 'home' elements in this action bar, leaving more space for other navigation elements. This includes logo and icon.
  • In member descriptions, be sure to link to relevant methods that use the constant or field.
    • Good: See also: setDisplayOptions(int), setDisplayOptions(int, int)

Methods

  • In the first sentence for a method description, briefly state what action the method performs.
    • Good: Checks whether this activity is in the process of being destroyed in order to be recreated with a new configuration.
  • In subsequent sentences of a method description, explain why and how to use the method, state any prerequisites that must be met before calling it, give details about exceptions that may occur, and specify any related APIs.
  • Document any dependencies (such as Android permissions) that are needed to call the method, and how the method behaves if such a dependency is missing.
    • Good: the method throws a SecurityException
  • Use present tense for all descriptions.
    • Good: Adds a new bird to the ornithology list.

Description

  • If a method performs an operation and returns some data, start the description with a verb describing the operation.
    • Good: Adds a new bird to the ornithology list and returns the ID of the new entry.
  • If it's a "getter" method and it returns a boolean, start with "Checks whether ...."
  • If it's a "getter" method and it returns something other than a boolean, start with "Gets the ...."
  • If a method has no return value, start with a verb such as "Sets the ...." (turning on an ability or setting), "Updates the ...." (updating a property), "Deletes the ...." (deleting something), or "Registers ...." (registering a callback or other element for later reference).
  • For a callback, start with "Called by ...." (for example, "Called by Android when ....").
    • Good: Called by Android when ....
  • For a callback, later in the description say "Subclasses implement this method to ...."
  • If it's a convenience method that constructs the class object, start with "Creates a ...."

Parameters

  • Capitalize the first word of a parameter description.
  • End a parameter description sentence or phrase with a period.
  • Begin descriptions of non-boolean parameters with "The" or "A" if possible.
    • Good: The ID of the bird you want to get.
  • For boolean parameters that tell the API to do or not do something, state what the API does if the parameter is true and if it's false.
    • Good: enableCertificateValidation: If true, validates the SSL certificate before proceeding. If false, trusts the certificate without validating it.
  • For boolean parameters that declare the already-established state of something, use the format "True if ...; false otherwise."
    • Good: True if the zoom is set; false otherwise.
  • In boolean parameter and return value descriptions, don't put the words "true" and "false" in code font or quotation marks.
  • For parameters with default behavior, explain what the behavior is for each value or range of values, and then say what the default value is.
  • Use the format Default: to explain the default value of a parameter.

Return values

  • Be as brief as possible in the return value's description; put any detailed information in the class description.
  • If the return value is anything other than a boolean, start with "The ...".
    • Good: The bird specified by the given ID.
  • If the return value is a boolean, use the format "True if ...; false otherwise."
    • Good: True if the bird is in the sanctuary; false otherwise.

Exceptions

  • In languages where the reference generator automatically inserts the word "Throws", begin your exception description with "If ...".
    • Good: If no key is assigned.
  • Where the reference generator doesn't insert "Throws", begin your exception description with "Thrown when ...".
    • Good: Thrown when no key is assigned.

Deprecations

  • When something is deprecated, tell the user what to use as a replacement.
    • Good: Deprecated. Use #CameraPose instead.
  • If you track your API with version numbers, mention which version something was first deprecated in.
  • Put the most important deprecation information in the first sentence of the description; use subsequent sentences to explain why something is deprecated and any other useful information.
  • If a method is deprecated, tell the reader what to do to make their code work.
    • Good: Deprecated. Access this field using the getField method.
