Command-line syntax

Compiled from the Google developer documentation style guide, Command-line syntax, licensed CC BY 4.0. Generated: edit the company rules instead, and turn Google rules off or change them there.

Best practices

  • Provide an inline link to the command reference, for example in the text that introduces the command or a series of steps.
    • Good: To connect to the instance, use the gcloud compute ssh command: gcloud compute ssh
  • Determine which arguments are needed to complete each task in the recommended way, and use as few optional arguments as possible.
  • Provide a click-to-copy command example that the reader doesn't need to edit after they copy it, including only runnable code and placeholder variables if possible.

Optional arguments in click-to-copy commands

  • Avoid using optional arguments, mutually exclusive arguments, or repeated arguments (square brackets, curly braces, pipes, and ellipses) in click-to-copy commands.
  • Remove optional arguments from click-to-copy commands if possible, using only the arguments necessary to complete the task for the most common use case, and always provide a link to the command reference.
    • Good: To get an aggregate list of all virtual machine (VM) instances in all zones for a project, use the gcloud compute instances list command: gcloud compute instances list If you want to narrow the list of VMs to a specific zone, use the previous command with the --zones flag.
  • Use separate code blocks for each option instead of optional-argument syntax in a click-to-copy command.
    • Good: To create a bootable Compute Engine image, use the gcloud compute images import command: gcloud compute images import IMAGE_NAME \ --source-file=SOURCE_FILE If you're importing an image with an existing license, specify the --byol flag: gcloud compute images import IMAGE_NAME \ --source-file=SOURCE_FILE \ --byol
  • Document optional arguments in separate tasks when it's best to treat different options in separate sections.
    • Good: Import a bootable virtual disk: If your virtual disk has a bootable operating system installed on it, run the following command: gcloud compute images import IMAGE_NAME \ --source-file=SOURCE_FILE Import a non-bootable virtual disk: If your virtual disk doesn't have a bootable operating system installed on it, include the --data-disk flag: gcloud compute images import IMAGE_NAME \ --source-file=SOURCE_FILE \ --data-disk
  • If you must include special characters to indicate optional arguments, let the reader know that the command contains optional arguments when you introduce the command.
    • Good: In the following example, you optionally specify the auto-delete subflag to keep or discard each disk when the VM is permanently deleted: gcloud compute instance-groups managed create-instance NAME \ --instance=VM_NAME \ --stateful-disk=device-name=DEVICE_NAME,source=DISK[,auto-delete=DELETE_RULE]

Format a command

  • To mark a block of code such as a lengthy command or a code sample, use the pre element.
  • When a command line exceeds 80 characters, add a line break before a character such as a single hyphen, double hyphen, underscore, or quotation marks.
  • After the first line of a split command, indent each line by four spaces to vertically align each line that follows a line break.
  • When you split a command line with a line break, end each line except the last line with the command-continuation character: a backslash preceded by a space ( \) for Linux or Cloud Shell, or a caret preceded by a space ( ^) for Windows.
    • Good: gcloud compute images import IMAGE_NAME \ --source-file=SOURCE_FILE
  • Format placeholder text in a command with placeholders.
  • Follow the command line with a descriptive list of the placeholders used in the command line.
  • When documenting a command-line option or argument, use end punctuation for complete sentences.
  • Don't use end punctuation for single words or noun phrases that document a command-line option or argument, unless there is a mix of sentences and noun phrases.
  • When you're documenting a bash or sh command, follow the quotation mark style in Google's shell style guide.

Command prompt

  • If your command-line instructions show multiple lines of input in one block, start each line of input with the prompt symbol.
    • Good: $ adb shell shell@ $ screencap /sdcard/screen.png shell@ $ exit $ adb pull /sdcard/screen.png
  • If you don't want users to copy the prompt symbol when they copy the command, turn off text selection for the symbol if you can, for example by using CSS.
  • Don't show the current directory path before the prompt, even if part of the instruction includes changing directories.
  • If the overall context of the command interface changes, such as from the local machine to a remote machine, add an additional prompt indicator for the new context.
    • Good: $ adb shell shell@ $ screencap /sdcard/screen.png shell@ $ exit $ adb pull /sdcard/screen.png
  • If your document includes both multi-line and one-line commands, use the command prompt ($) for all of the commands in the document for consistency.
  • If your command-line instructions include a combination of input and output lines, use separate code blocks for input and output.
    • Good: $ cat ~/.ssh/my-ssh-key.pub The output is similar to the following: ssh-rsa KEY_VALUE USERNAME

Optional arguments

  • Use square brackets around an argument to indicate that it's optional.
    • Good: gcloud dns GROUP [GLOBAL_FLAG] [FILENAME]
  • If there's more than one optional argument, enclose each item in its own set of square brackets.
    • Good: gcloud dns GROUP [GLOBAL_FLAG] [FILENAME]

Mutually exclusive arguments

  • Use curly braces to indicate that the reader must choose one and only one of the items inside the braces, and use a pipe ( | ) to separate each choice.
    • Good: {FILE_1 | FILE_2}

Arguments that can repeat

  • Use three dots and no spaces ( ... ) to indicate that the reader can specify multiple values for the argument.
    • Good: gcloud dns GROUP [GLOBAL_FLAG ...]

Output from commands

  • Add output only if it adds value, for example if the reader needs to copy a value from the output or verify a value in the output.
  • If you are showing output, separate the command from the output with an introductory phrase such as "The output is similar to the following:" or "The output is the following:", customized if you want to call out something about the output.
    • Good: The output is similar to the following, in which the IP column shows the IP address for each resource:
  • To indicate that one or more lines of output are omitted from sample output, use three dots and no spaces ( ... ) on a separate line.
    • Good: Reading file status Upload done, resetting board... ... Wakeup reason: 0
  • Do not use the ellipsis character ( … ) to indicate omitted lines of output; use three dots ( ... ).

Command-line terminology

  • Avoid mapping nomenclature of the gcloud CLI's commands to Linux commands; Linux commands use options, parameters, arguments, and specialized syntax elements rather than the gcloud catchall terms flag and option.
  • Describe what the entire command does rather than what its individual elements are called, unless the reader must know the name of the command-line element.

gcloud commands

  • In docs, refer to gcloud command-line contents generally as commands, even though the gcloud CLI's syntax distinguishes between a command and a command group.
  • In the gcloud CLI, call any element other than the command or group name itself a flag, and call a value that a command or flag takes, such as a region value, an argument.

Example command with multiple elements

  • Use option as a catchall term, in addition to flag, when you don't want to mire the reader in specialized nomenclature.

Linux commands

  • Refer to an argument that specifies a path in a Linux command as only a path.

Linux signals

  • Use the vocabulary of Linux signals, such as kill, only in the context of process control.
  • When describing SIGKILL, a signal sent to kill a process, do not substitute cancel, end, exit, quit, stop, or terminate.
  • When describing SIGTERM, a signal sent as a request to terminate a process, do not substitute cancel, end, exit, quit, or stop.
  • When describing SIGQUIT, a signal sent from a keyboard to quit a process, do not substitute cancel, end, exit, quit, or stop.
  • When describing SIGINT, a signal sent to interrupt a process immediately, do not substitute suspend, end, exit, pause, or terminate.
  • When describing SIGPAUSE, a signal that tells a process to pause, or sleep, do not substitute cancel or interrupt.
  • When describing SIGSUSPEND, a signal sent to temporarily suspend execution of a process, do not substitute pause or exit.
  • When describing SIGSTOP, a signal sent to stop execution of a process for later continuation, do not substitute cancel, end, exit, interrupt, quit, or terminate.
